## Current DSH architecture acceptance: process-local streams

The user explicitly accepted loss of unresolved output on a hard crash and selected DSH as the architecture authority. This section supersedes the historical draft/projection implementation below.

- Removed persistent draft facts, kinds, readers, patches and the 250 ms / 4 KiB checkpoint writer. Streams accumulate in process memory and settle output, continuation, usage and actual stream records once.
- Removed persisted prepared HTTP bodies, wire templates, JSON-path bindings, prior-request fragments and selected historical message arrays. `AgentContextBuild` is not Codable. `AgentSessionRequest` contains request evidence and current-turn context; canonical messages own conversation history.
- The original user, settled answer, thinking and tool payload references use their actual message/execution identities. Equal text cannot redirect a new answer to a user message or an earlier execution.
- Orderly cancellation merges the live prefix into final answer/thinking and settles it once. Cold recovery sees only committed output, reconciles existing business receipts and never redispatches. Source authorization still protects retained content; no-content recovery does not depend on an irrelevant content read.
- The execution inspector now labels its data as request context, added context and metadata. It does not present these records as the exact historical HTTP request body.

## Historical follow-up repair after inspecting an actual session

The first verification gate did not cover the production stream shape sufficiently. Inspecting the five-turn, six-request development session found `system/message` before its `step/start`, a missing canonical result for a denied tool, repeated cumulative transcript middles in byte patches, duplicated tool definitions and repeated terminal thinking. That journal had 256 lines and 289,772 bytes; 105 draft records accounted for 173,580 bytes (59.9%). It is personal runtime data and is not included in the repository.

The repair enforces turn/step relations on both append and replay, including reads through the persistent index. Admission now writes `turn/start`, the route, `step/start`, `system/message`, then the user's message in one transaction. Every tool outcome, including a denial without a payload, has a canonical `tool/result` with its status, reason and exact call-event reference. Repeated provider call IDs in different turns resolve by their event sequence. Missing tool observations are rejected instead of being invented as plugin messages.

Transcript checkpoints use structural block, stream and continuation deltas. They preserve exact UTF-8, chunk timings, JSON null values and provider continuation data. A new attempt resets its transcript and continuation even when the output shape is unchanged; same-attempt patches must extend the correct committed base. Thinking accumulated across model steps references the ordered canonical reasoning blocks from the same execution. Provider-shaped tool definitions reference the canonical request header where their actual bytes agree. Request metadata omits reconstructable null placeholders and redundant wrappers.

The repair's verification is scoped to these changes and supersedes the initial gate for their current behavior:

## Historical comparison against a user-supplied DSH session

The subsequent real-session comparison exposes remaining structural problems; the earlier passing checks do not establish complete DSH alignment. The supplied `/Users/alwyn/Downloads/session.v3.jsonl` and the current Mira development session both contain two user turns, three main-loop model calls and one tool invocation. Their first prompts differ, their tools differ, and DSH also records a separate title-model request. These are comparable conversational workflows, not an identical-workload performance benchmark. Aggregate results are in `/tmp/mira-dsh-comparison.json`; no personal transcript or provider credentials are copied into this document.

| Measure | DSH | Mira |
|---|---:|---:|
| Uncompressed JSONL bytes | 64,811 | 106,522 |
| Physical lines | 38 | 121 |
| Tool definitions | 26 | 8 |
| System-message and request-header record bytes | 33,601 | 4,947 |
| Durable draft records | 0 | 46 |
| Durable draft record bytes | 0 | 49,378 |
| Main-loop request-projection record bytes | 0 | 11,300 |

The 46 Mira drafts comprise 19 thinking, five answer and 22 transcript records. Final assistant reasoning and answer text total 3,896 UTF-8 bytes. Counting actual stored text payloads across the display drafts, transcript block edits, transcript stream chunks/block ends and final assistant content/stream yields 27,269 bytes, almost seven copies of the text before JSON framing and identity metadata. DSH also intentionally retains content, stream chunks and block-end content: its 1,542 bytes of assistant text occupy three such representations. Thus retaining final content plus stream is shared behavior; Mira's additional draft representations and permanent checkpoint history are the excess. Incremental patches reduced one form of repetition without removing duplicated ownership.

DSH's loop derives each request from the current canonical header and admitted message surface (`agent-loop/src/agent.ts`, `buildRequest`). Its live stream events are process-local, and completion/interruption/error settles one `assistant/message` or `assistant/attempt`. Mira instead maintains typed input selections plus a provider-wire template, JSON-path bindings, previous-request references and lifecycle facts. All three requests in this Mira sample were reconstructed locally; their order and tool-result association are correct. Nevertheless, these parallel representations remain unnecessarily complex for the intended session contract. Copying DSH's transient-stream approach directly would also change Mira's hard-crash draft recovery guarantee, which must be accounted for explicitly when removing the duplication.

Content equality currently substitutes for ownership in some references. In the third Mira request, the current assistant's `replayMessage` points at the first response because both continuation payloads are empty and equal. The first request also binds one search tool's identical schema to another search tool's header entry. These reconstruct the same JSON in this sample, but the links obscure semantic provenance. References should follow their actual message/tool owner; empty continuation data does not need a cross-message reference.

The two providers use different wire protocols: DSH's recorded replay state identifies DeepSeek Messages, whose local adapter sends `/v1/messages` with structured thinking/tool blocks and signatures; Mira's frozen route uses Chat Completions with `reasoning_content`, `tool_calls` and function definitions. DSH explicitly records high reasoning effort and a 256,000-token output cap; Mira records provider-default thinking and a 4,096-token cap. These differences do not by themselves indicate malformed API input. DSH does not put all fixed context into the system message: tools belong to `request/header`, while project instructions, runtime context and skill catalog are attributed user-surface messages.

The content comparison also exposes a product issue: a simple address preference causes Mira to attempt a persistent memory write, receive an authorization denial, and explain that failure in its answer. Its memory-tool instructions leave the model to interpret what counts as explicit saving intent, while the implementation uses a narrower intent recognizer. This needs a consistent memory-intent contract and a specific rejection reason; changing logging fields cannot correct the behavior. No new model request was sent during this comparison.
